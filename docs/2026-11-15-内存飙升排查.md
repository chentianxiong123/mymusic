# 2026-11-15 MyGo 播放时内存飙到 400MB+ 排查记录

## 背景

MyGo 是我给 HomeMusic（B站音乐播放器）做的原生客户端支线——同进程直调主线域包（单二进制、自绘 UI、绕开 WebView）。功能上跑通了播放闭环，但一对比资源占用就觉得不对劲：

- 自绘本来图的就是"省内存"（不用塞 WebKit 引擎）
- 结果我这边 idle 就 150MB，一播放直接干到 430MB+

旁边主线 wails3 + htmx 版（hcexp）看起来才 240MB，一度怀疑自己把 WebView 不小心塞进去了。

## 问题现象

| 状态 | RSS | CPU |
|---|---|---|
| MyGo 空闲 | 153MB | 0.5% |
| MyGo 播放 | **431MB** | 6.4~10% |
| 主线 hcexp 主进程 | 233MB | 2% |

播放时内存比空闲多 **280MB**，而且播放结束后钉死不回落。

## 排查过程

### 第一轮：怀疑塞了 WebView（排除）

```bash
ldd /tmp/mymusic-native-pb | grep -iE "webkit|gtk"
ldd /tmp/mymusic-native-pb | wc -l           # 3
grep -iE "webkit|javascriptcore|wpe" /proc/$PID/maps | wc -l   # 0
```

**结果：一个 WebKit 映射都没有，动态库总共 3 个。** 对比主线 hcexp 是 173 个动态库。WebView 嫌疑排除——冤枉它了。

### 第二轮：对比口径错了（重要弯路）

第一次对比是 `ps aux | grep hcexp` = 291MB vs MyGo 435MB，看起来 MyGo 更胖。**但漏了 WebKitWebProcess**：

```bash
ps aux | grep -E "[w]ails3/bin/hcexp|[W]ebKitWeb"
# hcexp 主进程              233MB
# WebKitWebProcess (渲染)   347MB   ← 之前完全没算
# bwrap 沙箱                 ~3MB
# ---------------------------
# 主线全家 = 587MB
```

补全后：**主线 587MB vs MyGo 431MB**，自绘反而是省的。教训：wails3/Electron 这类应用内存必须把子进程一起算，只看主进程就是自欺欺人。

### 第三轮：SIGQUIT goroutine dump 抓 CPU

Go 程序直接 `kill -QUIT <pid>` 会把所有 goroutine 栈打到 stderr（顺带把进程干掉，正好用来安全关播放——声卡先 `pactl get-sink-mute` 确认 mute 了再操作）：

```
goroutine 247 [syscall, locked to thread]:
  mygo/audio/output_linux.go:124   ← PulseAudio 输出线程
goroutine 246 [sync.Cond.Wait]:
  mygo/audio/source.go:96          ← 音频解码 source
goroutine 54-57 [chan receive, 3 minutes]:
  mygo/internal/raster/team.go:75  ← 光栅渲染线程（空闲）
```

CPU 大头 = 音频输出 + 解码，属播放正常开销（**静音≠停止解码**，音量 0 也在全速解 AAC）。

### 第四轮：smaps 拆内存分布

```bash
# 空闲 vs 播放中 RSS 分布
# 空闲: libLLVM 45MB + heap 21MB + anon 16MB + 二进制 14MB
# 播放: anon 272MB (单块 256MB!) + heap 30MB + 字体 16MB(粗体被加载)
```

关键发现：**播放时出现一个 256MB 的单一匿名映射**（`20c41e000000`，256MB 对齐，全部 RSS 在物理内存里，内容几乎全零），空闲状态下根本没有。

附带发现：idle 基线里 libLLVM 45MB + libgallium 13.6MB = **58MB 是 mesa llvmpipe 软件渲染**（这机器无 GPU 加速，GTK 用 LLVM JIT 光栅化）。这是固定成本，跟播放无关。

### 第五轮：gctrace 定案

```bash
GODEBUG=gctrace=1 MYGO_DEMO=1 /tmp/mymusic-native-pb
```

```
gc 12 @1.377s  11->11->10 MB
gc 13 @1.385s  22->23->21 MB
gc 14 @1.421s  42->43->40 MB
gc 15 @1.438s  85->85->67 MB
gc 16 @1.481s  134->134->120 MB
gc 17 @2.509s  240->240->190 MB   ← live 190MB
```

**1.4 秒内 Go heap 从 11MB 冲到 240MB**，时间点正好是 demo 启动流程：

```go
a.search()           // 搜"周杰伦" → 20 条结果
→ 每条 loadCover()   // 20 张封面并发下载 + 解码
a.play(first)
```

### 第六轮：代码追溯，锁定真凶

```go
// player.go
img, err := ui.DecodeImage(data)   // ← 全尺寸原图解码
a.covers[bvid] = img               // ← 永久缓存，无上限、无缩放、无驱逐
```

```go
// mygo ui/bitmap.go
func DecodeBitmap(data []byte) (*Bitmap, error) {
    s, err := decodeImage(data)    // image.Decode → 原图尺寸
    ...
}
// internal/scene/scene.go
// Pix 是 premultiplied RGBA, 4*W*H 字节

// ui/widgets.go DecodeImage → DecodeBitmap → *Bitmap
// Bitmap 还持有: 原 JPEG 字节(remake 闭包) + mipmap levels[] 缩小层
```

B站搜索结果的封面 URL 是原图（1280×720 ~ 1920×1080），解码成 RGBA：

- 1280×720×4 ≈ 3.7MB/张，1920×1080×4 ≈ 8.3MB/张
- 20 张 ≈ **130~160MB**，加上 remake 的原始 JPEG 字节 + mipmap levels ≈ 200MB+
- Go GC 不立即把内存还给 OS → RSS 钉在峰值

**而音频链路只占几 MB**：

```go
// mygo_output.go：先下载到磁盘临时文件
f, _ := os.CreateTemp("", "mymusic-mygo-*.m4a")
io.Copy(f, resp.Body)          // 落盘，不进内存
...
p, _ := audio.OpenStream(r)    // 流式解码
// mygo audio/source.go: ring = max(sampleRate,4096) frames
// = 48000 * 2ch * 4B = 384KB
```

## 结论

**MyGo 播放时 430MB 的构成：**

| 项目 | 大小 |
|---|---|
| anon / Go heap（封面 RGBA 位图 20 张 + mipmap + 原始 JPEG 字节） | ~240MB |
| mesa 软件渲染（libLLVM + libgallium，固定成本） | 58MB |
| Go runtime baseline + 二进制 + 字体 | ~100MB |
| **音频链路（下载到磁盘 + 384KB ring buffer）** | **< 10MB** |

**一句话：不是音频、不是 WebView、不是自绘，是搜索结果 20 张封面原图全部解码成 RGBA 位图永久缓存。**

## 顺带对比：WebView 那边为什么没这问题

同样的搜索（周杰伦 20 结果），xdotool 驱动 hcexp 窗口点搜索框输入回车：

| | MyGo | WebKit |
|---|---|---|
| 搜索后涨幅 | **+240MB（heap，永久）** | **+59MB（347→406），20s 后回落到 394** |

原因看主线 htmx 模板（`go/web/templates/results.html`）：

```html
<img src="{{coverURL .Cover}}" loading="lazy" class="w-12 h-9 object-cover">
```

1. `loading="lazy"` —— 只解码视口内的图
2. WebKit ImageCache 按内存压力自动驱逐/LRU（实测回落就是它在回收）
3. 只解码显示尺寸（48×36px），不需要整张原图像素

而 MyGo 的 `loadCover`：一次并发全 load、原图全尺寸解码、map 永久缓存。**纯代码问题，不是框架问题。**

## 修复（已完成）

三个改动（`player.go` / `main.go`）：

1. **缩放缓存**：`loadCover` 里 `image.Decode` 后走自写 `scaleTo(img, 160)` 双线性缩到长边 160px，再 `ui.NewBitmap` 存缓存——原图 1280x720 RGBA ≈ 3.7MB/张 → 缩略 160x160 ≈ 100KB/张
2. **LRU 上限**：`coverOrder` 记录插入顺序，超过 `coverLimit=60` 张时驱逐最旧（保留当前播放曲目）
3. **换页清理**：`search()` 替换结果时清掉非当前曲目的封面缓存和顺序表
4. 兜底：非位图（SVG 等）仍走 `ui.DecodeImage`，不做缩略

实测对比（同 demo：搜索周杰伦 20 结果 + 播放）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| RSS（播放中） | 431MB | **230MB（-47%）** |
| Go heap 峰值 | 240MB | **61MB（-75%）** |
| heap live | 190MB | **20MB** |
| RSS（空闲） | 153MB | 152MB（不变） |

剩的 230MB ≈ 空闲基线 152MB（含 mesa 软件渲染 58MB）+ 音频/字体/播放链路 ~78MB，符合预期。

## 坑与教训

1. **wails3/Electron 对比必须算子进程**：`WebKitWebProcess` 347MB 不算进去就是假账（291 vs 435 的假象）。
2. **Go 程序 RSS 高别只看堆**：smaps 里匿名映射 + gctrace 组合拳才能分清 Go 堆/外部库/raster 固定成本。
3. **libLLVM 45MB 是 mesa llvmpipe**：无 GPU 环境 GTK 软件渲染的固定成本，别误当成代码泄漏。
4. **静音不等于停止解码**：音频线程照样全速跑，CPU 归因要想到这层。
5. **`kill -QUIT` 能看栈也能关播放**：调试 Go 长驻播放进程的顺手招。
6. **`pkill -f "xxx"` 会匹配自己的命令行自杀（exit 143）**：echo/grep 里出现同名字符串就把自己杀了，用 `pgrep -x` 或先 `pgrep -f` 拿 PID 再 kill。
7. **root shell 里 systemctl --user 连不上**：`XDG_RUNTIME_DIR` 指向 `/run/user/0` 但桌面 bus 在 `/run/user/1000`（a1），要手动 export 正确的 XDG_RUNTIME_DIR。
8. **`ps` 的 %CPU 是进程生命周期平均值**，不是瞬时值——"10.3%" 其实平均 6.4%，判断要看清口径。
