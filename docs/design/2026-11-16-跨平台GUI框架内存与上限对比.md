# 跨平台 GUI 框架内存与上限对比 —— 一次实测记录

> 日期：2026-11-16
> 场景：给 mymusic 项目选壳时，把手上几套 GUI 方案的实际内存和渲染上限摸了一遍底
> 核心结论：**「看起来小」≠「真的小」—— python 版空闲时 68MB，但一旦播放，靠子进程（PyQt5 挂件 157MB + mpv 96MB）撑到 324MB，反而比 Go 原生版还费。内存大小不取决于功能多少，取决于渲染架构。**

---

## 一、背景

mymusic 是家庭音乐播放器（B 站音乐 · 个人免费）。项目里有好几套并行实现，我想搞清楚到底哪套省内存、哪套 UI 上限高，于是把每套都拉起来实测。

涉及的方案：
| 方案 | 技术栈 | 说明 |
|---|---|---|
| **~/sh/music**（python 版） | Python 3.13 + **Tkinter** + mpv + PyQt5 挂件 | 最早期，功能最少 |
| **mygo**（mymusic-native） | **Go + GTK3 原生**（无 webview） | 支线，纯 native |
| **主线 wails3**（hcexp） | **Go + wails v3 + WebKitGTK 6.0** | 主线，WebView |
| **cc-switch** | Rust + **Tauri + WebKitGTK 4.1** | 系统工具（对照） |
| **clash-verge** | Rust + **Tauri + WebKitGTK 4.1** | 代理客户端（对照） |

---

## 二、实测内存（全部 RSS，递归统计含子进程）

### 2.1 关键：python 版「看起来小，实际靠子进程」

这是我踩的最大的坑。**只看主进程会被骗**：

| 采样时机 | python 版总内存 | 组成 |
|---|---|---|
| **空闲**（刚启动，未播放） | **68 MB** | 只有 Tkinter 主窗 |
| **播放中**（挂件+mpv 都起来） | **324 MB** | Tk 79MB + **PyQt5 挂件 157MB** + **mpv 96MB** |

拆开看：
```
music.py（Tk 主 GUI）      79 MB   ← 主进程确实小
lyric_widget.py（PyQt5 挂件） 157 MB  ← 最重！是主程序 2 倍
mpv（播放内核）            96 MB   ← 播放时的独立子进程
─────────────────────────────
合计                      324 MB
```

**教训**：python 版省内存是**假象**。Tkinter 主窗确实只有 79MB，但它把「歌词挂件」和「播放内核」甩给了**两个独立子进程**（PyQt5 + mpv），加起来 324MB。**内存不能只看主进程，必须递归统计整个进程树。**

### 2.2 全家福实测（完整播放/运行状态）

| 方案 | 实测内存 | 进程构成 | 渲染架构 |
|---|---|---|---|
| **mygo**（Go+GTK3） | **≈ 205 MB** | 单进程（主窗+挂件+播放全内置） | GTK3 原生，无 webview |
| **python**（Tkinter） | **≈ 324 MB** | 3 进程（Tk 79 + PyQt5 157 + mpv 96） | Tk 软件渲染 + 2 个子进程 |
| **主线 wails3** | **≈ 689 MB** | 主进程 250 + WebProcess 352 + NetProc 90 | WebKitGTK 6.0 |
| **cc-switch** | **≈ 636 MB** | 主进程 272 + WebProcess 302 + NetProc 77 | WebKitGTK 4.1 |
| **clash-verge** | **619 MB ~ 1.4 GB** | 主进程 250 + **1~3 个 WebProcess** 各 350-400 | WebKitGTK 4.1 |

### 2.3 关键规律：内存跟「功能多少」无关，跟「渲染架构」强相关

- **纯 native**（Tkinter / GTK3）：205~324MB，功能多也省。
- **WebView**（wails3 / Tauri）：**600MB 起步**，多出来的 ~400MB 全是**浏览器渲染引擎（WebKitWebProcess）**。
- 哪怕是同一个功能的程序，**用 WebView 就比 native 多花 400MB**。

## 三、UI 美感 / 渲染上限对比

**先看渲染栈（实测 `/proc/<pid>/maps`）：**

| 方案 | GL/EGL 库数 | 渲染方式 |
|---|---|---|
| python（Tkinter） | **0**（纯软件） | X11 + XRender + 字体光栅化 |
| mygo（GTK3） | **25**（libGLX_mesa/EGL） | Cairo + GL 硬件加速 |
| wails3 / Tauri（WebKit） | 大量 | Skia + GL + 完整 DOM/CSS 引擎 |

**上限能力排序：Tkinter << GTK3 native < WebView**

| 架构 | 能做的最高级效果 | 上限 |
|---|---|---|
| **Tkinter** | 矩形/文本/色块 | 2000 年代桌面软件 |
| **GTK3 native** | 圆角/渐变/阴影/自绘动画 | 接近现代 web，但**手算坐标** |
| **WebView** | 全 CSS/动画/backdrop-blur/WebGL | **浏览器级，无上限** |

**实测截图佐证：**
- python 版：经典 Tk 控件（下拉框、滚动条、直角按钮），无圆角/渐变/动画。
- mygo 歌词挂件：半透明黑底 + 白色歌词 + 底部高亮，字体平滑。
- 主线 wails3：紫色渐变胶囊「搜索」、圆角卡片，现代 web 风。

**关键洞察：**
1. **Tkinter 的天花板是「画不出现代效果」**（无 GPU、无半透明、无圆角/渐变/动画），**是架构性限制，不是没用心**。
2. **GTK3 能画出接近 web 的美感**，但**代价是开发成本**——mygo 的 `player_ui.go` 花 55KB 手写圆角/渐变/胶囊/hover，且无 CSS 布局引擎，**布局全靠手算坐标**。
3. **WebView 上限最高、开发最省**——直接 CSS/Tailwind，浏览器做所有渲染。

## 四、clash-verge 的 WebView 泄漏 bug（额外发现）

实测中发现 clash-verge **每次「轻量模式」切换后，新建一个 `WebKitWebProcess` 且旧的不销毁**：

```
重启后（1 个 webview）     745 MB
3 分 02 秒（2 个 webview） 1156 MB
4 分 42 秒（3 个 webview） 1459 MB
```

每个新 WebProcess 一出生就 **340~390MB**，从不回收。重启只暂时清零，用几分钟又累积。

**已提 issue**：https://github.com/clash-verge-rev/clash-verge-rev/issues/8657
（与 #7568 长期缓慢泄漏不同，这是「切换即新增进程、旧进程不销毁」）

## 五、结论 / 决策参考

1. **内存排序（完整播放态）**：mygo(205) < python(324) < cc-switch(636) < wails3 主线(689) < clash(619~1459)
2. **python 版「省内存」只在空闲时成立**（68MB），播放时靠 PyQt5+mpv 子进程撑到 324MB，**反超 mygo**。
3. **要最省内存**：选 **mygo（Go + GTK3 原生）**——单进程 205MB，无 webview、无独立播放子进程。
4. **要最美/最高上限/最省开发**：选 **主线 wails3（WebView）**——689MB 换浏览器级渲染能力。
5. **别信「主进程内存」**——必须递归统计整个进程树，否则会像 python 版那样被骗。
6. **WebView 类应用（wails3/cc-switch/clash）都是 600MB+**，这是 WebKit 渲染引擎的固定成本，砍功能也省不掉。

## 六、踩过的坑（复盘）

- ❌ **只看主进程 RSS**：差点得出「python 版 68MB 最省」的错误结论，实际播放时 324MB。
- ❌ **按名字 grep 漏子进程**：clash 第一次只报 383MB，漏了它的 WebKit 子进程（实际 1150MB+）。
- ❌ **只按直接 PPID 找**：wails3 的 WebKitWebProcess 嵌套在 `bwrap` 沙箱里（父是 bwrap 不是主进程），直接 PPID 找不到，**要用递归**。
- ✅ **正确方法**：`ps -eo pid,ppid` 递归收集所有后代，逐个读 `/proc/<pid>/status` 的 VmRSS 累加。
- ✅ **判断渲染架构**：读 `/proc/<pid>/maps` 里 `webkit` / `gtk` / `libGL` 的映射数量，一眼看出是 native 还是 WebView、有无 GPU。
