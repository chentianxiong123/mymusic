# 1.2.5 逐层抽象重构设计：统一 SongRef，取流只有一份实现

## 目标

修掉 1.1.0 暴露的问题：`Target.Play(songID)` 名字通用、实际只吃 bvid；
`/api/v1/music/stream/{bvid}` 写死 B站。做到：

- 加新音源 → 输出层零改动
- 加新输出目标 → 音源层零改动
- 同一首歌在「本机/蓝牙/DLNA/音箱」之间切换，标识不变

## 分层与每层的抽象契约

### 第 0 层：统一歌曲引用 `SongRef`（新增，放主线 `homecast/model` 包）

> 依赖方向：homecast（主线）不能 import mygo 的子包。所以 `SongRef` 必须放主线
> `go/model/`，mygo 侧与主线各层都 import `homecast/model`。mygo 自己的 `model`
> 包保留 `LyricLine`，需要时 type alias 或直接在签名里用 `homecast/model.SongRef`。

```go
type SongRef struct {
    Source string `json:"source"` // "bilibili"/"netease"/"qqmusic"/"local"/...
    ID     string `json:"id"`     // 音源内唯一 id（bvid / 网易云 id / 本地路径）
    Title  string `json:"title"`
    Artist string `json:"artist"`
    Cover  string `json:"cover"`
    URL    string `json:"url,omitempty"` // 已知直链（可选）
}
```

**规则**：所有层之间传 `SongRef`，不再传裸 `string songID`。

- 主线 `playback.Song` 保留 BVID 字段兼容 web/wails3，但新增 `Source`/`ID` 字段；
  新代码一律用 `Ref()` 方法拿 `SongRef`。
- `bilibili.SearchItem` → `playback.Song` 的转换处填 `Source:"bilibili", ID:BVID`。
- 搜索页 `source.Song` 转 `SearchItem` 时把来源塞进 `Typename`（已有字段）→
  `toSong()` 读 Typename 填 Source。这样**不动 SearchItem 结构**，web 线兼容。

### 第 1 层：音源层 `source.MusicSource`（已有，保持）

```go
Search(keyword string, page, size int) ([]Song, int, error)
GetStream(ref SongRef, quality int) (*Stream, error)   // 改参数：id string → ref SongRef
GetLyric(ref SongRef, keywords []string, sid int) ([]model.LyricLine, error)
```

改动点：`GetStream`/`GetLyric` 签名从裸 id 改成 SongRef，编译器会逼所有调用处处理 source。
实现内部仍用 `ref.ID`（B站=bvid，网易云=数字 id），零业务逻辑改动。

### 第 2 层：取流/供给层（核心重构）

统一一个函数，所有消费者共用：

```go
// homecast/service/streamsupply —— 唯一取流入口
type Supplier struct {
    Sources map[string]source.MusicSource  // 音源注册表（插件来源）
    Cache   *cache.CacheService            // m4s 共享缓存
    Xcoder  *transcode.Transcoder          // mp3 转码缓存
}

// Resolve 把 SongRef 变成可直接喂给播放端/远程设备的 mp3（或 file://）
func (s *Supplier) Resolve(ref SongRef, quality int) (path string, err error)
```

流程（只有这一份）：
```
src := Sources[ref.Source]
stream := src.GetStream(ref, quality)
if stream.URL 是 file:// → 直接返回路径
if xcoder 命中(ref.ID) → 直接返回 mp3 路径
m4s := cache.Ensure(ref.ID, stream.URL, referer)
mp3 := xcoder.EnsureMP3(m4s, ref.ID, qn)
return mp3
```

消费者：
- **本机播放** `MyGoOutput.loadAndPlay()` → 调 `Supplier.Resolve()`，删掉自己那份
  `ensureM4S`/转码分支（共用基础设施终于有统一入口）。
- **HTTP 供给端点** `/api/v1/music/stream` → 调 `Supplier.Resolve()`，按 `source`/`id`
  参数分发，不再写死 `GetAudioStream(bvid)`。
- **DLNA** → 端点 URL 带 `source=xxx&id=yyy`。
- **音箱** → 主线 `SpeakerService.Play(bvid)` 保持 B站专用（音箱协议只认 B站 URL），
  但 mygo 侧入口先检查 `ref.Source == "bilibili"`，否则拒绝并提示，不假装支持。

### 第 3 层：输出目标层 `target.Target`（改签名）

```go
Play(ref model.SongRef, opts PlayOpts) error
```

- `LocalPlayer` → `MyGoOutput.Play(ref)` → Supplier
- `Bluetooth` → 忽略 ref（系统路由），只做音频路由（无需取流）
- `CastDevice` → `SetURL(supplyURL(ref))`（DLNA 设备自己拉本机 mp3）
- `XiaoaiSpeaker` → 检查 ref.Source，仅 B站可投

### 第 4 层：UI/控制层

- `app.current` 从 `track{bvid}` 改成带 `SongRef`（新增字段 `ref`），
  UI 显示仍读 `bvid/title`，不改渲染代码。
- `castTo/playToSpeaker/PlayBluetooth` 传 `a.current.ref` 而不是裸 bvid。
- 非 B站源时 DLNA/音箱按钮禁用或点击提示（明确能力边界）。

## 实现差异（相对原设计）

- `Supplier` 放 mygo 侧（`mygo/supply.go`），不放主线：主线 homecast 不能反向依赖
  mygo 的 source 插件表；通过 `func() map[string]source.MusicSource` 函数注入解决。
- `playback.Output.Play(bvid, opts)` 接口签名保持不变（web/wails3 兼容），
  改在 `PlayOpts` 加 `Source/ID` 字段传递跨源引用——避免波及主线所有 Output 实现。
- `bilibili.SearchItem` 加 `Src` 字段传来源；B站结果留空=默认 bilibili，老数据兼容。
- 老端点 `/api/v1/music/stream/{bvid}` 保留（音箱 + web 兼容），
  新端点 `/api/v1/music/stream/ref?source=&id=` 走通用 Supplier。

## 不变的约束

- 不删 mygo iOS、wails iOS CI；通用 APK 3 ABI 不动
- CI 全手动；不触发
- 数据目录 `mymusic-mygo` 不改；模块路径不改
- 前端不放开发日志/解释性注释
- 省资源优先：缓存共用、不重复 IO
