# 2026-11-26 搜索分页口径统一：过滤/排序下沉 UI 单页

## 背景

搜索分页出现"页数对不上"的体感。排查发现根因只有一处：

`go/service/music/search.go` 的 `music.Search()` 在返回前做了 `FilterSongs()`：
- `res.List` 被过滤（B站请求 40 条 → 返回 25 条）
- `res.Total` 没动（还是 API 的 `numResults`）

**一个返回值里混了两种口径**。UI 按 `total / size` 算页数、按过滤后的 list 显示 → 每页条数忽多忽少、后几页可能空白。

## 架构决策

用户定调：

> 分页搜索是靠 API 的。过滤和排序走前端单页，不要污染接口，不然不统一。

### 分层

| 层 | 职责 | 不做 |
|---|---|---|
| 数据层 `source.Search` / `music.Search` | 纯 API 透传：songs + total 同口径 | 不过滤、不排序 |
| UI 层 `presentSongs()` | 本页渲染前：过滤非歌 + rank 排序 | 不改数据、不改分页 |

所有音源（B站/网易云/JS 插件/本地）的数据契约统一为：
```
Search(keyword, page, size) → (songs 原样, total 原样)
```
分页严格靠 API：`页数 = total / size`，翻页 = `page+1` 重新请求。

### 为什么过滤只在 B站有

过滤规则依赖的字段全是 B站特有：`typename`（分区标签）、标题里的"翻唱/cover/教学/电台"、视频时长分布。其他源搜索结果本身就是歌曲，不需要这层。它是 B站搜索的**呈现策略**，不是通用数据逻辑——所以放 UI 单页，不进接口。

### 改动

1. `go/service/music/search.go`：
   - `SearchRaw()` 去掉时长过滤 + rank 排序，纯 API 透传
   - `Search()` = `SearchRaw()`（不再调 FilterSongs）
   - 导出 `SongRank(typename, title, durationSec)` 供 UI 排序
2. `mygo/search_present.go`（新）：`presentSongs()` 过滤 + 排序，只作用于本页且不修改原切片
3. `mygo/search_view.go`：渲染前调 `presentSongs`，标题显示"显示 X / 本页 Y 首"；本页全 filtered → "本页内容已过滤"

### 代价（明确的取舍）

- 每页显示条数不固定（第 1 页显示 25、第 2 页 31）——诚实换整齐，不补位、不重排
- 想每页稳定 N 首就得动态多请求补位，那会破坏分页边界导致重复/丢失——不做

## 测试

- `go/service/music/music_test.go`：改为验证纯透传（5 条原样、顺序不变、total=5）
- `mygo/search_present_test.go`：过滤掉教学、排序顺序、原切片不被修改
- 全量 homecast + native 测试通过；Win/Mac 交叉编译通过
