# 2026-11-25 mymusic 输出源抽象失误复盘

## 起因

输出源收尾，用户问："DLNA 和蓝牙是不是没什么代码量？" 我说不多，顺手做了一轮：蓝牙后端抽象、本机面板、DLNA 改投本机 mp3 供给端点。

做完我说"DLNA 投本机 mp3 供给端点，什么音源都能放"——**这句是错的**。用户当场拆穿："那不就是了吗，你乱搞。你根本就没抽象好每一层细节。"

## 我错在哪

我改的是 `cast_page.go` 里投送 URL：

```go
URL: castStreamURL(a.current.bvid)
```

这个 URL 指向 `/api/v1/music/stream/{bvid}?mp3=1`。我看了一眼端点会走 mp3 转码分支，就以为它是通用音频供给。**没往下看它取流的代码**：

```go
// go/service/music/music.go
func (m *MusicService) GetAudioStream(bvid string, quality int) (*bilibili.AudioStreamResult, error) {
    // view 拿 cid → playurl 取 DASH 音频
}
```

写死 B站。参数名叫 `bvid`，不是 `songID`——我把它当 `songID` 用了。

所以真实情况是：

| 目标 | 能放什么 | 为什么 |
|---|---|---|
| 本机 | 全音源 | 播放端按 `src` 插件走 `GetStream()` |
| 蓝牙 | 全音源 | 系统音频路由，播放端放什么它出什么 |
| DLNA | **只有 B站** | 供给端点只认 bvid → B站 playurl |
| 小爱音箱 | **只有 B站** | `SpeakerService.Play(bvid, ...)` → 同一个 B站端点 |

我"修好"的只是把 DLNA 从主线代理 URL（在 mygo 里根本拉不到）换成了本机 B站专用 URL（能拉到了，但仍然是 B站专用）。修了一个 bug，没修抽象。

## 逐层看抽象到哪了

这次翻车不是"没抽象"，是**抽象做了一半，接口名骗人**：

| 层 | 接口 | 实际 | 问题 |
|---|---|---|---|
| 播放层 | `source.MusicSource.Search/GetStream/GetLyric` | 真的多源 | ✅ 抽象到位 |
| 输出目标层 | `target.Target.Play(songID, opts)` | 参数实际是 bvid | ❌ 名字通用，语义专用 |
| 供给层 | `/api/v1/music/stream/{bvid}` | B站 view+playurl | ❌ 无 source 维度 |
| 音箱层 | `SpeakerService.Play(bvid, did, ...)` | B站专用 | 主线历史包袱，不走 source 插件 |
| 蓝牙层 | `BtBackend.RouteTo(id)` | 系统音频路由 | ✅ 真通用，不碰音源 |

`Target.Play(songID)` 是最坑的——名字让我以为"传个歌曲 ID 就行"，实际只有 B站 ID 能活。**不完整的抽象比不抽象更危险**：不抽象大家知道那是专用的；半抽象的接口会让人误以为它能吃所有输入。

## 为什么越复杂的项目越需要抽象，因为要复用

这次是活教材。同一个"取流 → 转 mp3 → 供给远程设备"的能力，被写了两遍：

- 本机播放：`MyGoOutput.loadAndPlay()` → `cache.Get/ensureM4S` → `xcoder.EnsureMP3`
- 音箱供给：`MusicHandler.Stream?did=xxx` → `streamSpeakerMP3()` → `ensureM4S` → `EnsureMP3`
- 我新加的 DLNA 供给：直接复用音箱那条（但只在 `did`/`mp3=1` 分支），等于又糊了一层

三处逻辑本质相同，但因为入口参数分别是 `bvid`/`bvid`/`songID`（其实还是 bvid），谁也不敢直接复用。于是每加一个输出目标就要重新接一次管线，每接一次就可能漏一个音源。

**抽象的价值不是"好看"，是"写一次，所有地方都能用"**：

1. **统一输入模型**：歌曲要有跨源标识（source + id + 可播 URL），不能让每一层自己猜"这个字符串是 BV 号还是网易云 ID"。
2. **统一取流能力**：`source.GetStream()` 是所有音源的共同入口。远程供给、本机播放、歌词、封面都应该走它，而不是各写一份 B站 playurl。
3. **统一转码/缓存**：m4s 缓存 + mp3 转码已经共用基础设施了，但入口没统一——这次就是入口没抽象导致我误用。
4. **接口名必须说真话**：`Play(songID)` 如果只吃 bvid，就该叫 `PlayBVID()`，或者把参数类型换成结构体让编译器逼你处理 source。

复用不是"复制粘贴同一段代码"，是"同一件事只有一个地方做"。这次我做到了表面复用（DLNA 复用了供给端点），但没做到本质复用（供给端点本身不通用）。

## 正确的抽象应该长什么样

```go
// 1. 跨源歌曲引用（所有层统一传这个）
type SongRef struct {
    Source string // "bilibili"/"netease"/"qqmusic"/...
    ID     string // 该源内的 id（bvid / songid / ...）
    URL    string // 已知直链（可选）
    Title  string
}

// 2. 统一供给端点：按 source 分发到对应插件的 GetStream
GET /api/v1/music/stream?source=netease&id=xxx&format=mp3
    → plugin.Source(source).GetStream(id)
    → cache(m4s) → xcoder.EnsureMP3 → serve

// 3. target.Target.Play(ref SongRef, opts) —— 参数类型本身强制跨源
```

这样 DLNA、音箱、本机、蓝牙（如果做应用内路由）都吃同一个 `SongRef`，取流只有一份实现。加新音源只改 `source` 插件，输出层零改动。

## 现状与待办

- [ ] 把 `target.PlayOpts` / `SongRef` 统一（当前 `Play(songID string)` 名不副实）
- [ ] 供给端点加 `source` 维度，按插件 `GetStream()` 取流（不再写死 `GetAudioStream(bvid)`）
- [ ] 音箱 `SpeakerService.PlayBVID()` 保持 B站专用现状，但 mygo 侧调用前先确认当前源是 bilibili；其它源暂时不投音箱（明确告知用户，不假装支持）
- [ ] DLNA 面板在非 B站源时禁用投送按钮或提示"当前仅支持 B站"，别再让人误以为全源可用
- [ ] 蓝牙因为走系统路由，真·全源可用——这条不用改

## 教训

- 改代码前先把调用链读到底，别看到"mp3"就以为通用。
- 接口名和参数名是承诺。`songID` 里塞 bvid 就是在撒谎。
- 半抽象最危险：它让人停止追问"这里到底支持什么"。
- 复杂项目里，复用是刚需而不是洁癖。多写一次取流逻辑，就多一处音源不一致。
