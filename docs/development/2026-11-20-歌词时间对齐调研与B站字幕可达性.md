# 歌词时间对齐调研与 B站字幕可达性（研究结论）

> 日期：2026-11-20 ｜ 项目：mymusic/mygo ｜ 场景：想把"无时间戳歌词"自动对齐到歌曲时间轴；检查 B站能否直接拿字幕当定时歌词
> 本文为**研究/推理结论**（脑测），未做实现与命中率实测。

---

## 0. 结论摘要（先看这个）

| 问题 | 结论 |
|---|---|
| 无时间戳歌词能否自动对齐？ | **概念 100% 可行**（成熟领域：Forced Alignment），**但 mygo 自包含做不到** |
| 为什么做不到？ | 对齐必需 **ASR/TTS**（文本→时间映射），**无纯 Go 实现**；成熟方案全是 Python/C++ |
| mygo 现实路径 | ① **云 API**（在线、简单） ② **cgo + whisper.cpp**（离线，破无-cgo，模型 ~400MB） |
| B站能拿字幕吗？ | **不能随便拿**：要登录 + 约一半视频真没有 |
| 非AI 包络互相关对齐？ | **PoC 失败**：谱质心/MFCC/能量/人声带占比对满配流行/摇滚歌**置信度恒低（标准分 1.5–2.5，BBC 门槛 >10）**，歌依赖 |
| **“起始位置对不上”的真因** | **≈匹配问题**：匹配到错版本（翻录/DJ/Live，编排/起句点不同），**不是对齐算法问题** |
| 对齐能不能搞？ | **不用搞**——时长重排找准版本后，同源 LRC 残留偏移 **+0.2~+0.8s**，现有 ±0.5s 手动微调够用 |
| 结论 | **定时歌词靠谱来源 = 音源自带 LRC**；**匹配准了自然就对齐了**（时长重排已落地） |

## 1. 歌词时间对齐 = Forced Alignment（强制对齐）

> "forced" 指：**我们自己提供参考文本（歌词）**，用 ASR 模型把这段文本强行对齐到音频时间轴。正是"歌 + 无时间戳歌词 → 自动标时间"的场景。**成熟领域**，非新东西。

### 1.1 概念可行性：100%

| 方案 | 说明 | 精度 |
|---|---|---|
| WhisperX（m-bain） | wav2vec2 词级强制对齐，**有"已知文本对齐"功能**（正合此场景） | 词级 |
| AutoLyrixAlign（chitralekha18） | **专为歌词设计**（歌唱适配声学模型 SAT，多声部） | 行级 ~0.5s |
| lyric-align（PyPI） | 处理副歌重复，均差 ≤0.5s | ~0.5s |
| easyaligner / mikezzb/lyrics-sync | 开源强制对齐 / 深度学习歌词对齐 | 好 |
| 在线服务（LyricTimestamps、Gliss） | 免装免 GPU，传音频返回时间戳 | 好 |

### 1.2 关键卡点：核心是神经网络 ASR，无纯 Go

- 对齐本质 = 文本→时间映射，必须有 **ASR（Whisper 类）** 或 **TTS** 做参照
- 所有成熟 ASR = Python/PyTorch（WhisperX/AutoLyrixAlign）或 C++（whisper.cpp）
- **纯 Go 神经 ASR 库：不存在**（搜索确认）
- whisper.cpp 有 Go 绑定（`ggerganov/whisper.cpp/bindings/go`），但**是 cgo**，且 **base 模型 ~400MB**

### 1.3 mygo 可行性（纯 Go / 无 cgo / 离线 / Android）

| 路径 | mygo 可行性 | 代价 |
|---|---|---|
| ① cgo + whisper.cpp | ⚠️ 破无-cgo；CPU 推理慢；Android 每架构 .so | cgo + 400MB |
| ② 云 API | ✅ 最省事；但**在线**+传音频（隐私）+可能付费 | 网络依赖 |
| ③ 外部进程（whisper.cpp 当 ffmpeg 调） | ⚠️ 桌面可行，Android 难 | 维护+体积 |
| ④ WASM whisper | ⚠️ 保纯 Go 但极慢 + WASM 100MB+ | 性能杀手 |
| ⑤ 纯 Go 自己写 | ❌ **不可行**——没 ASR/TTS 做不了文本→时间映射 | — |

**判定：概念可行、技术成熟，但对 mygo"纯 Go 无 cgo"是死结。**

### 1.4 坑（若将来做）

- **中文/普通话**：需适配预训练语音模型（有专门论文），比英文难
- **副歌重复**：经典失败点（WhisperX 有 issue；lyric-align 专门处理）
- **多声部/背景音乐**：干扰识别（AutoLyrixAlign 用歌唱适配模型对抗）
- **精度**：~0.5s 字级，够滚动歌词，个别词会偏

## 2. B站字幕可达性（实测）

### 2.1 机制

- `GET https://api.bilibili.com/x/player/v2?bvid=&cid=` → `data.subtitle.subtitles[]`
- 每条 `{from, to, content}`——**带时间戳，本质就是 LRC**（yt-dlp 用 `json2srt` 转 SRT）

### 2.2 实测发现（12 个视频，含音乐/非音乐）

**两个拦路虎**：

| 拦路虎 | 证据 |
|---|---|
| ① **要登录** | 匿名调用字幕全 0；`need_login_subtitle` 区分"有字幕需登录"vs"真没有"；yt-dlp 源码注释 "login required for CC subtitle" |
| ② **不是每首都有** | 测 6 视频 `need_login_subtitle`：**3 True（有字幕要登录）、3 False（真没有）** |

抽样（need_login_subtitle）：
- ✅ 有字幕（要登录）：周杰伦《枫》、皇后大道西、出狱/犯罪类视频
- ❌ 真没有：袁洁莹 MV、周杰伦《给我一首歌的时间》、人生一串纪录片

### 2.3 判定

> **"随便一首 B站歌拿到字幕" 不成立。** 约一半有字幕，一半真没有（MV/纯音频常无 CC）；**有字幕的也要 SESSDATA 登录**才能取 `subtitle_url`。mygo 匿名播放 B站 → **字幕不能当可靠歌词源**。

## 3. 总体结论与决策

1. **字幕（B站）不是救星**：不可靠（要登录 + 非每首有），不能作为定时歌词的可靠来源。
2. **定时歌词靠谱来源 = 音源自带 LRC**（咪咕/网易/B站/本地多数已给）。
3. **无 LRC 时的对齐 = Forced Alignment**：概念可行，但**依赖 ASR/TTS，无纯 Go 实现**；非 AI 包络互相关 PoC 也失败（见 §4）。
4. **决策**：**mygo 不做自包含自动对齐**。若将来要，走 **云 API**（简单、在线）或 **cgo whisper.cpp**（离线、重、破戒）。
5. **修正（重要）**：实测发现**“起始位置对不上”本质是匹配问题**——匹配到错版本（翻录/DJ/Live 编排不同）导致 LRC 与音频对不上。**时长重排修复后，同源 LRC 自动对齐**（残留 +0.2~+0.8s），见 §4。**对齐算法先不急，先修匹配**。
6. 本调研为**可行性研究**；§4 的 PoC 与时长重排为实测。

## 4. 非 AI 对齐 PoC 与「对齐≈匹配」发现（实测）

### 4.1 非 AI 包络/特征互相关 PoC（失败）

思路：把 **LRC 行时间包络**（有词=1）与 **音频人声活动特征** 互相关，峰值滞后 = 起始偏移。测了五种特征（纯 DSP，无 AI）：

| 特征 | 海阔天空(摇滚) | 枫(钢琴抒情) | 皇后大道西 |
|---|---|---|---|
| 能量包络 | ❌ 失败 | ❌ 失败 | ❌ |
| 谱通量 | ❌ 失败 | ❌ 失败 | ❌ |
| **谱质心** | ❌ **假峰**（基线 +3.2s，真实 ~+1.2s） | ✅ **6/6 找回**（误差≤0.4s） | ⚠️ 部分 |
| MFCC 能量 | ❌ 标准分 1.7 | ❌ 1.7 | — |
| 人声带占比 | ❌ 1.4–2.4 | ❌ 1.5–2.5 | — |

**根因**：满配编曲的歌**伴奏连续不断，填满人声间隙**→ 能量/音色类特征**区分不出“唱/不唱”**→ 互相关面是平的。谱质心对钢琴抒情歌可行（伴奏与人声有对比），对摇滚歌失败（吉他/鼓主导）——**歌依赖，不稳健**。

**公认方法对照**：BBC 官方 `audio-offset-finder` = **MFCC 序列互相关**，是 **audio↔audio** 找偏移（精度 ~0.01s + **标准分置信度**，>10 可信、<5 需人工）；不适用于 **audio↔LRC**（LRC 是文本时间戳，无对应特征）。**标准分机制本身是对的**——它正确地告诉我们“算不准”（全程 <5）。

### 4.2 关键发现：对齐 ≈ 匹配（实测）

逐句对比 **同源音频 + 同源 LRC**（都是网易云同一 sid）的“LRC 时间戳 vs 音频实际人声起点”，只取“前有停顿的新起句”（可靠）：

| 歌（同源版本） | 可靠新起句 | 偏移均值 | 中位 | σ |
|---|---|---|---|---|
| 光辉岁月(302s) | 12 | **+0.16s** | +0.15s | **0.50s** |
| 海阔天空(239s) | 10 | **+0.65s** | +0.35s | 1.08s |
| 千千阙歌(347s) | 21 | **+0.80s** | +0.77s | 1.14s |

**全部落在 ±1s 内（≈对齐）**，残留偏移 **+0.2~+0.8s**，落进 mygo 现有 **±0.5s 手动微调**范围。

> **同源 LRC 天然按该音频打的点，所以本来就对齐。** “起始位置对不上”是真凶是**匹配到错版本**（翻录/DJ/Live 编排不同、起句点不同）——之前谱质心测出的 +3.2s 假峰，就是匹配错版本的假象。

### 4.3 时长重排（已落地，修复匹配）

- **问题**：网易云搜索相关度把翻录/不同版本排前面（海阔天空 239s 翻录在 326s 原版前），mygo 取“第一个有词候选”→ 匹配错版本。
- **修法**：候选**先按时长重排**（`music.LyricDuration(bvid)` 取 B站视频时长=歌曲时长作期望值）：±2s 满分 / ±5s 良 / ±10s 及格，**稳定排序**保持网易云相关度兜底；无期望时长/全不匹配则保持原序不误伤。再取重排后第一个 ≥3 行候选。
- **live 验证**：海阔天空期望 326s → **326s 原版从网易云第 3 位提到第 1 位**（id=347230），239s 翻录/Live 沉底。
- 全仓测试绿（`TestRankByDuration` + go/mygo 全量）。

### 4.3.1 标题相似度打分（已落地，把“不同歌”沉底）

时长重排解决了“错版本”，但还有一类漏网：**网易云把完全不同的歌搜进来**。例：搜“枫 周杰伦”，因为《默》(李荣浩/周杰伦 Live) 含“周杰伦”，网易云把它排进来——mygo 取“第一个有词候选”就可能**拿到《默》的歌词配到《枫》上**。

- **修法**：候选再叠一层**标题相似度**（`titleScore`，学 musicxx 的“版本字段”思路）：歌名**归一**（剥各类括号内容 + 剥离版本/音质词：钢琴版/Live/DJ/Remix/Cover/原唱/无损/4K…）后比较——**相同 100 / 包含 80 / 共享 2 字子串 60 / 无重叠 0**。
- **三层字典序**：`rankCandidates` = **时长主** → **标题次** → **网易云相关度兜底**（两次 `sort.SliceStable`，后者优先；无期望值则不排，不误伤）。
- **live 验证**：搜“枫 周杰伦”，`默 (Live)` 从第 5 位**沉底到第 7 位**；两首《枫》提前。
- 全仓测试绿（`TestTitleScore`/`TestCoreTitle`/`TestRankCandidatesTitleDemotesOtherSong`）。

### 4.4 musicxx（拟声）歌词匹配方法对照

- **自建歌词库**（用户上传/制作），非网易云曲库
- 早期 MySQL 全文索引**失败**（bili 标题冗余【4K超清】、歌手混入、英文分词误配、内存大）
- 25 年重构：**智能识别**（提取真歌名/歌手列表/别名/繁简/错别字）+ **自研分词** + **BM25 相关性打分**（**字段权重**：标题 > 歌手 > 版本 DJ/remix）+ **`duration` 参数参与搜索**
- 运行期增删改同步索引；违禁词过滤
- **启示**：musicxx 用**加权打分**而非“第一个结果”，且**把 duration 纳入搜索**——mygo 时长重排即此思路的落地（网易云已给相关度，mygo 只需补时长维度）
