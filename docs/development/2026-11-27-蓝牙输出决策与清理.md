# 2026-11-27 蓝牙输出：从自己实现到交还系统

## 背景

mymusic 一直有一套蓝牙输出抽象（`target/bt_backend.go` + 各平台后端 + 投送页蓝牙面板），提供"发现蓝牙 / 连接 / 音频到此 / 恢复本机"。实测一路暴露问题后，最终决定**整个删掉**：蓝牙音频本来走系统通道，应用不该插手。

这篇是架构决策记录，个人折腾细节见 `~/桌面/2026-11-27-mymusic蓝牙输出折腾记录.md`。

## 问题现象

用户实测三个问题：

1. 点"连接"按钮 GUI 卡死（看起来像崩溃）
2. 设备根本没连、没有 `bluez_output.*` sink，却显示"音频到此"按钮，点了没反应
3. 系统里已经连上蓝牙音箱，软件却显示"未连接"

## 排查过程

### 1. 确认"发现蓝牙"是假的

`ScanBluetooth()` → `BtBackend.List()` → `bluetoothctl paired-devices`，只读本机已配对记录，从不执行 `scan on`。接口名说谎。

### 2. 确认 mygo 框架没有内置蓝牙 API

`mygo@v0.10.0` 全部顶层模块无 Bluetooth 相关能力；`plugins/permissionflow` 只做 macOS CoreBluetooth 权限申请，不提供设备发现/连接。项目自己写外部命令对接是唯一路子。

### 3. 全平台"真扫描"难度评估

| 平台 | 手段 | 难度 | 结论 |
|---|---|---|---|
| Linux | `bluetoothctl scan on/off` | 低 | 可做 |
| macOS | `blueutil --inquiry`（私有 IOBluetooth API） | 低 | 可做但脆弱 |
| Windows | 无干净 CLI，PnP 枚举接近"已发现" | 中 | 只能跳系统设置 |
| Android | `startDiscovery()` + `BLUETOOTH_SCAN`/`ACCESS_FINE_LOCATION` | 中 | 要碰 manifest + 权限 UI |
| iOS | 经典蓝牙不开放 | — | 不做 |

### 4. 方向判断：从已配对设备里选是最通用解

配对是系统职责；投音频必须先配对；全平台都已覆盖、权限最轻。用户认可这个方向，但要求过滤出音频设备。

### 5. 音频设备过滤（提交 22d8052）

实测 `bluetoothctl info` 的 UUID：

- 小爱音箱 / Nokia 3208c：有 `Audio Source (110a)` / `Headset AG (1112)` → 音频设备
- BT5.2 Mouse：只有 HID / Battery → 非音频

公共 `bt_audio.go`：`hasAudioUUID()`（六类 A2DP/HFP UUID）+ `isAudioName()`（名称关键词兜底）。各端填 `BtDevice.Supported`。

### 6. 修复"连接"卡死与假按钮（提交 16e72ea）

- 根因：`ConnectBluetooth` 在 UI 回调同步跑 `bluetoothctl connect`（阻塞到超时）。别的按钮都用 `go`，唯独它同步。
- 根因：`Supported` 只表示"有音频能力"，不表示"当前可投"。
- 修：`BtDevice` 加 `Ready`（已连接 + 音频端点存在），UI 砍掉"连接"/"断开"，只对 `Ready` 显示"音频到此"；"发现蓝牙"改名"刷新"。

### 7. 修复已连接设备漏判（提交 9695bf6）

```
bluetoothctl devices Connected:
Device 40:31:3C:63:5D:FC 小爱音箱-5846
pactl list short sinks:
1218 bluez_output.40_31_3C_63_5D_FC.1 ... RUNNING
```

但项目读 `connected=false`。根因：`len(f) >= 4` 判断 `Device <MAC> <名字>`，中文设备名无空格只有 3 个字段被漏掉；有空格的 `BT5.2 Mouse` 反而误判为已连。改 `len(f) >= 3` + 抽纯函数 + 回归测试。

### 8. Mock 推流验证链路真假（提交 f6476b1）

用户怀疑音频是假的，要求先 mock 成功再说。

```bash
ffmpeg -f lavfi -i 'sine=frequency=1000:duration=20' /tmp/mock-tone.wav
ffmpeg -f pulse -i bluez_output.40_31_3C_63_5D_FC.1.monitor -t 12 /tmp/mock-capture.wav &
paplay --device=bluez_output.40_31_3C_63_5D_FC.1 /tmp/mock-tone.wav &
```

结果：sink `SUSPENDED` → `RUNNING`，monitor 录回 2.2MB/12s，`mean -12.9dB / max -3.4dB`——链路是真的。

调用项目真实 `RouteTo()`：3 条 `sink-input` 从 `56`（扬声器）迁到 `1218`（蓝牙），`RUNNING`；`RouteToLocal()` 迁回。

真凶：

1. `PlayBluetooth` 成功后调 `pauseLocalForCast()` —— 蓝牙是本机音频路由，暂停本机播放直接没声。逻辑写反。
2. `RouteTo` 只 `set-default-sink`，不迁移已存在的流。补 `move-sink-input`。

### 9. 决策：整个删掉

用户："蓝牙本就走系统通道出声音的啊，我们根本不需要管啊对吧。"

从 3 个 bug 反推：每多管一层多一个 bug。系统已经做好了这件事。

## 方案对比：能不能只接管本软件的流

用户追问"蓝牙吃整个系统的流，做在软件里是不是能只接管我们这一个，代价如何"。

先纠正概念：**PipeWire/PulseAudio 路由本来就是逐流的**，`move-sink-input` 就是单独移动一条流，`set-default-sink` 只影响之后新建的流。

| 维度 | 结论 |
|---|---|
| Linux | `move-sink-input` 按 PID 过滤可做 |
| macOS | `SwitchAudioSource` 只能切系统默认；CoreAudio per-process 是私有 API |
| Windows | 没有公开 per-app 设备路由 API（只有 per-app 音量） |
| Android | 完全系统自动路由 |
| 流重建 | 切歌时 `audio.Player` 新建流，需持续跟踪 + 订阅 PipeWire 事件 |
| 产品语义 | 用户在系统切蓝牙，预期所有声音都走蓝牙；强行只让音乐走反直觉 |
| 已有能力 | `local_config.go` 已有"输出声卡"设置页，列所有 `pactl sinks`（含蓝牙），点选即切 |

**结论：不值得做。**

## 决策

- **删除**整个蓝牙输出抽象层：`target/bt_*.go`、`target/bluetooth.go`、`target_panel_bluetooth.go`、`BtDevice`、host 接口蓝牙方法、能力表里的 `bluetooth`、插件页蓝牙项。
- **保留** `local_config.go` 的"输出声卡"设置页——用户想让本软件走蓝牙时，在那里选蓝牙 sink 即可（副作用是系统默认一起切，这符合用户正常预期）。
- **保留** DLNA / 小爱音箱投送面板——它们是真正的远端 URL 投送，和蓝牙不是一个性质。

## 坑与教训

1. 系统已经做好的事别重做；app 插手蓝牙输出只会引入 bug。
2. 接口名必须说真话：只读已配对列表就叫"刷新"，别叫"发现"。
3. `Supported`（能力）和 `Ready`（当前可用）是两个字段，不能混。
4. 解析命令行输出要拿真实样本，别凭想象写字段数判断。
5. UI 回调里绝不跑阻塞命令；`bluetoothctl connect` 能卡几十秒。
6. 用户说"是假的"时先实测——mock 推流 5 分钟就能分清是链路假还是逻辑假。
