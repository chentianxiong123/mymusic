# 一体化插件模型设计（v1.3.x 重构）

## 问题：同一个平台被拆成多个插件条目

现状：插件身份 = `Type + "/" + Name`（如 `source/netease`、`lyric/netease`），设置键
`plugin:<type>/<name>/<key>`。同一个平台按能力拆成多个条目，导致：

1. 登录态割裂——音源能读到的 cookie，歌词/推荐插件读不到（之前用 account 层打补丁，但根因没除）。
2. 插件页重复——网易云在「音源」分页和「歌词」分页各出现一次。
3. 一人做一个平台要改多处——违反"一个人完整交付一个插件"的直觉。

## 目标

**插件身份 = 平台 key（唯一），能力是插件的属性，不是身份的一部分。**

```
现状： plugin:source/netease/cookie  +  plugin:lyric/netease/xxx  +  infos["source/netease"], infos["lyric/netease"]
目标： plugin:netease/cookie         +  infos["netease"]  Capabilities:[source,lyric,recommend]
```

- 一个平台 = 一个条目，一个目录（JS 插件零编译拖文件，能力声明在 `capabilities`）。
- 登录态天然共享（一份设置，不再需要按 type 拆）。
- 歌词能力**注册**（插件实现 `lyric()` → 进入歌词插件列表）与**绑定**（音源插件选哪个歌词插件）是两件事，不冲突：
  - 实现歌词 API 的插件自动注册为歌词提供者；
  - 没实现歌词的音源插件，在其详情页选别的歌词插件（保留 `lyricbind/<source>` / 歌级绑定）。

## 数据模型

### Info（插件元数据）

```go
type Info struct {
    Name         string   // 平台 key（唯一身份）
    DisplayName  string   // 展示名（网易云/B站）
    Type         string   // 兼容字段：主能力（source/lyric/target）
    Capabilities []string // 能力列表：source / lyric / recommend / target
    Icon, Version, Desc string
    Order int
}
```

注册表 key 从 `Type+"/"+Name` 改为 `Name`。`InfoNames(type)` 改为按 `Capabilities` 过滤。

### 设置存储

- 新键：`plugin:<name>/<key>`（按平台，不再按 type）。
- 迁移：启动时扫描旧键 `plugin:source/<name>/*`、`plugin:lyric/<name>/*`，搬到 `plugin:<name>/*`（保留旧键空值兼容）。
- `account.go` 的 `plugin:account/<platform>/cookie` 合并进来：cookie 就是 `plugin:<name>/cookie`。

### 启用/顺序/绑定

- 启用状态：`plugin:<name>/enabled`（旧 `source/<name>` 等迁移）。
- 顺序：`mygo_pluginorder` JSON key 从 `source/netease` 改成 `netease`。
- 歌词绑定：`lyricbind/<source>` 语义不变（值是歌词插件 key），仍保留——它表达"这个音源用谁的歌词"，与能力注册正交。

## 能力注册表

`RegisterSource/RegisterLyric/RegisterRecommend/RegisterTarget` 保持独立注册表（按能力取用），
但元数据（Info）按平台合并：注册时若同名 Info 已存在，合并 Capabilities 而非新增条目。

JS 插件 `capabilities: ["source","lyric","recommend"]` 一个插件注册多个能力，设置只存一份
（`plugin:<key>/*`）。

## UI（插件页）

不再按 type 分页，改为**一个平台一个卡片**：
- 卡片显示平台名 + 能力标签（音源/歌词/推荐/目标）+ 启用开关
- 详情页按能力分区：音源配置、歌词配置、登录、歌词源绑定、推荐配置
- 拖拽排序直接排平台条目

## 迁移策略

1. 启动时一次性迁移旧设置键（source/lyric/account → 平台键），写入后旧键清空。
2. 顺序 JSON 的 key 从 `type/name` 转 `name`。
3. 歌词绑定 key 不变（`lyricbind/<source>` 的值本来就是插件名）。
4. 设置声明（RegisterSettings）仍按能力注册，但底层存储走平台键——UI 不变，存储统一。

## 分步实施

1. `plugin/info.go` Info 加 Capabilities + key 改 Name；注册表合并同平台。
2. `plugin/setting.go` 键改 `plugin:<name>/<key>` + 旧键迁移。
3. `plugin/account.go` cookie 键统一到 `plugin:<name>/cookie`（保留 API，内部改）。
4. 内置注册（main.go）：netease 的 source + lyric 合成一个 Info（Capabilities 两个）。
5. JS 插件加载：capabilities 多能力注册，设置命名空间按 key。
6. 插件页：三类分页改平台卡片 + 详情页能力分区。
7. 顺序/启用持久化迁移。
8. 全量测试 + 交叉编译；旧数据迁移测试。

## 明确不做

- 不做"插件实现账号 API"——登录协议留宿主（JS 无 crypto/二维码能力，凭据不下放插件）。
- 不做"平台包 + 重新编译"——坚持零编译拖文件。
- 能力注册表仍按能力分离（source/lyric/recommend/target 各管各的取用），合并的是**身份/设置/UI**，不是把能力混成一坨。
